## 作業目的

日本の App Store を中心に、**個人開発者・小規模法人・小規模チームが出していて実際にヒットしているアプリ**を
自動実行のたびに継続調査し、「個人＋AI で現実的に再現・差別化・収益化できる候補」を progress 上で比較・
意思決定できる状態にする。単発調査ではなく蓄積が目的。

**単なるアイデア出しは禁止**。現在順位・ランキング推移・評価件数・Android DL 数など、実績を確認できたアプリだけを
根拠URL付きで扱う。

## 実施内容

### データ構造（最重要）

- **アプリ1本 = 1レコード**。キーは App Store URL の数値ID（`/id123456789`）を正規化したもの。同じアプリで行が増えない
- 調査するたびに **スナップショットを append**。過去データは消さない（同一時刻の再投入だけ上書きして二重投入を吸収）
- 差分（カテゴリ順位 / 総合順位 / 評価件数 / レビュー件数 / Play評価件数 / DL変化）は**読み出し時に前回比で計算**するため、
  後から何度でも再計算できる
- 確認できなかった値は `null` のまま保持し、**推測で埋めない**（画面では「確認できない」と表示）

### 判定ルールをコード側で強制

| 条件 | 判定 |
|---|---|
| `developerScale = excluded`（大手・大規模パブリッシャー） | 対象外 |
| `monetization = paid`（買い切り・有料DL） | 対象外 |
| `developerScale = unknown`（規模不明） | **参考候補**（本採用にしない） |
| 個人 / 小規模法人 | 本採用候補 |

### 画面 `/app-market-research`

- 一覧列: アプリ / 開発規模 / ヒットタイプ / 現在順位 / 30日推移 / 評価数・増加 / Android DL / 収益モデル / 再現性 / 判定
- 行展開: なぜ伸びたか・差別化案・サーバー/運用/コンテンツ負荷・版権・**前回との差分**・**調査履歴**・情報源URL
- アプリ名から App Store、リンクから Google Play を開ける
- 絞り込み: ヒット型 / 開発規模 / 収益モデル / 再現性★ / カテゴリ
- 並び替え: 個人で作る価値順 / 直近上昇順 / 継続ヒット順 / 再現性順 / 現在順位順 / 評価増加順 / 調査が新しい順

### 自動実行への組み込み

- 定時起動（11/14/16/23時）のたびに `ensureMarketResearchTask()` が作業予約へ調査タスクを**1件だけ**積む
- 未完了の同種タスクがあるときは積まない（溜めて工場を圧迫しない）
- 実行は既存の dispatch と安全ゲートに乗る
- プロンプトに固定で埋め込んだもの: 件数方針（3本前後・弱い候補で数合わせしない・有力な新規が1本ならそれでよい）/
  対象と除外 / ヒット判定（surging・sustained・both、リリース6〜12か月で50位以内は強評価）/
  **既出アプリ一覧**（重複登録の防止）/ POST仕様 / 再現性★の付け方 / 報告フォーマット

## 危険ポイント

- 調査プロンプトは executor に Web 参照を任せる設計。**情報源URLの記録を必須にしているが、値の正しさは executor の精度に依存する**。
  一覧の「情報源」から人間が検証できるようにしてある
- 自動実行のたびに1件積むため、executor が失敗し続けると同じタスクが `needs_retry` で滞留する可能性がある
  （その間は新しい調査タスクを積まない設計なので暴走はしない）
- 判定ルール（買い切り除外・規模不明は参考候補）はコード側で強制しているが、`developerScale` の分類自体は executor の判断
