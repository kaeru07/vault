## 原因分析

### 1. 「工場を作る作業」が「工場でアプリを作る作業」を食った

アプリ系ゴールの done 11件は、**全て progress 自身の機能追加**だった。

> 設計一覧ページ追加 / 進行状態バッジ / アプリ案詳細モーダル / 案生成の種を market-research まで拡張 /
> 品質操縦ループ / 設計一覧からの仕様編集 / 新アプリ候補の自動提案 …

**アプリ本体を1歩進めたゴールは done の中に1件も無い。** 工場は「工場の改良」を自分の仕事として選び続けた。

### 2. 完成条件が「工場の機能が動いたか」で判定されていた

ゴール『アプリを一定レベル(App Store公開仕様)まで指示なしで自走完成させ完成したら確認』は
**2026-07-09 に done=100/100** になっている。

しかし done になったのは「自走フローの**仕組みが出来た**」ことに対してで、
そのフローで**実際にアプリが完成したわけではない**。仕組みの完成とアプリの完成が同じ完了条件で扱われていた。

### 3. 空振りが完了として積み上がった

ファイル変更を伴ったRunは **49%**。「（出力なし）」で終わったRunが completed 扱いになる問題は
2026-08-24 にゲートを入れて塞いだが、**それまでの2か月半は回数だけが増え続けた**。

### 4. 生成物が正本に接続されなかった

自動生成の置き場 `apps/generated` には Expo 試作2本（`ny01-mahjong-analyzer` / `shogi-kakoi-trainer`）が
残ったが、どちらも 2026-07-20 で更新停止。方針として不採用が確定し、
**正本のリポジトリには一度も接続されなかった**。

### 5. 最後の1マイルが構造的に人間依存

ストア提出・審査・公開は安全のため自動化していない。
よって「公開」をゴールに置く限り、**自動実行だけでは定義上ゴールに到達できない設計**だった。

## レビューしてほしい点

1. 「工場の改良」と「アプリを作る」が同じキューで競合し、前者が勝ち続けた。**どう分離すべきか**
2. **仕組みの完成とアプリの完成を、同じ done で扱ってよかったのか**
3. 公開が人間依存である以上、自動実行のゴールは「公開」ではなく**「提出直前まで」に置くべきだった**のではないか
4. 88日・1,480回を投じた結果として、**この構造は続ける価値があるか。畳むべきか**
